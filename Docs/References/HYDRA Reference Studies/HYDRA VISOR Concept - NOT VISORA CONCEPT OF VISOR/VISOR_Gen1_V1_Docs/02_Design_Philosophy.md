# 02 - VISOR Paradigms & Design Philosophy

**Part of:** VISOR Protocol & Implementation Guide (Gen1 V1)
**Last Updated:** 2025-11-10

---

## Overview

This document explains the core design principles behind VISOR, the responsibility boundaries between components, and the evolvability strategy.

---

## 2.1 Core Principles

### "Thin at edges, strong in core"

**Philosophy:** Keep the harness layer minimal, move intelligence server-side

**Rationale:**
- LLM chat interfaces are diverse and unpredictable
- Thin client = easier to implement in new environments
- Server-side = one place to fix bugs, add features
- Protocol logic centralized = consistency across clients

**In Practice:**
- ChatGPTVisor: Frame detection + state machine only
- VisorGateway: Parsing + routing only
- Node: All policy decisions (auth, caps, batching, flow)

---

### Protocol-native passthrough

**Philosophy:** MCP payloads pass through VISOR unchanged

**Rationale:**
- No transformation = no bugs
- No wrapper overhead = simpler debugging
- Protocol semantics preserved = compatibility guaranteed

**In Practice:**
```javascript
// VISOR input
mcp() {
  { "name": "tools/call", "id": "r1", "arguments": {...} }
};

// Envelope output (payload unchanged)
{
  "op": "mcp",
  "payload": { "name": "tools/call", "id": "r1", "arguments": {...} }
}
```

VISOR adds metadata (`.headers`, `.meta`) but **never modifies payload**.

---

### Separation of Concerns

**Philosophy:** Each layer owns specific responsibilities, nothing more

**Layers:**

1. **Harness (ChatGPTVisor)**
   - Frame detection in LLM output
   - UI send queue management
   - Downstream buffering during generation
   - NO: batching, caps, policy

2. **Gateway (VisorGateway)**
   - Parse VISOR → Envelope
   - WebSocket text I/O
   - Connection lifecycle
   - NO: business logic, auth, protocol semantics

3. **Node (Future)**
   - Auth & session management
   - Caps & quotas enforcement
   - Batching & flow control
   - Service routing
   - NO: protocol details, frame syntax, UI

4. **Services (VisorHydraService)**
   - Business logic only
   - Tool execution
   - Resource access
   - NO: envelopes, framing, networking

## 2.4 Evolvability Strategy

### Additive Changes Only

**Principle:** New features added, never breaking old ones

**How:**
- New codecs: opt-in via `c` parameter (`json1e`, `yaml1s`)
- New protocols: opt-in via new `protoName` (`xmcp`, `http`)
- New dotted sections: existing parsers ignore unknown sections
- New envelope fields: old code ignores unknown fields

**Example:**
```javascript
// v1 client (today)
mcp() { { "name": "echo" } };

// v2 client (future) - both work
mcp(c="json1e") { { "name": "echo" } };
xmcp() { { "name": "echo", "hydra_extensions": {...} } };
```

---

### Version Negotiation

**Protocol Version:** Via `v` parameter
```javascript
mcp(v="1.0") { ... };     // Explicit v1.0
mcp(v="1.1") { ... };     // Future v1.1
mcp(v="latest") { ... };  // Default (server decides)
```

**Codec Version:** Via `c` parameter
```javascript
mcp(c="json1s") { ... };  // JSON strict-ish (current)
mcp(c="json1e") { ... };  // JSON embedded (future)
mcp(c="yaml1s") { ... };  // YAML strict (future)
```

**Envelope Schema:** Separate versioning (not in VISOR)
```javascript
.meta = { "schema": "mcp://schemas/tools/call/1.0" };  // v1.0 schema
.meta = { "schema": "mcp://schemas/tools/call/2.0" };  // v2.0 schema
```

---

### Forward Compatibility

**Parsers tolerate unknown elements:**
- Unknown dotted sections skipped
- Unknown prolog params ignored
- Unknown envelope fields preserved

**Example:**
```javascript
// Future VISOR with unknown section
mcp() {
  .headers = { "Priority": 5 };
  .extensions = { "custom_field": "value" };  // Unknown, ignored
  { "name": "echo" }
};

// v1 parser processes this successfully:
// - Extracts .headers
// - Ignores .extensions (logs warning)
// - Parses payload normally
```

**Implementation:** `Json1sParser.cs:260-386` (ExtractDottedSectionsAndPayload)

---

### Backward Compatibility

**Existing fences valid forever:**
```javascript
// This v1 fence will always work
mcp() { { "name": "echo" } };
```

**No breaking changes:**
- Can't change grammar in incompatible ways
- Can't remove support for old codecs
- Can't change envelope field meanings

**Migration Path:**
- Old clients work with new servers (ignore new features)
- New clients work with old servers (detect capabilities)
- Graceful degradation (use old features if new unavailable)

## Design Trade-offs

### Chosen: Simplicity over Optimization

**Trade-off:** VISOR doesn't batch or optimize - server does

**Why:**
- Harness stays simple (easier to port to new LLMs)
- Server can evolve batching without client changes
- Policy centralized (quotas, caps, priorities)

**Cost:**
- More network round-trips (acceptable for MVP)
- Less client-side optimization (server makes up for it)

---

### Chosen: Text-based over Binary

**Trade-off:** VISOR uses text fences, not binary framing

**Why:**
- Works in any LLM chat interface (text-only)
- Human-readable (debugging easier)
- LLM-friendly (model can learn to generate)

**Cost:**
- Slightly larger payloads (JSON text vs binary)
- Parsing overhead (regex + JSON parse)

**Future:** Binary codecs available via `c` parameter if needed

---

### Chosen: Protocol-agnostic Harness

**Trade-off:** VISOR doesn't know MCP semantics

**Why:**
- Can carry other protocols later (`xmcp`, `http`, `grpc`)
- MCP changes don't require VISOR changes
- Harness reusable across protocols

**Cost:**
- Can't optimize for MCP-specific patterns
- No MCP-aware compression or batching

---

## Design Principles Summary

1. **Thin at edges, strong in core** - Minimal client, smart server
2. **Protocol-native passthrough** - No payload transformation
3. **Separation of concerns** - Clear layer boundaries
4. **Additive evolution** - Never break existing code
5. **Explicit opt-in** - New features require explicit request
6. **Tolerance for unknowns** - Ignore what you don't understand
7. **Text-first** - Human-readable, LLM-friendly
8. **Protocol-agnostic** - MCP today, others tomorrow
